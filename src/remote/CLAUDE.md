# src/remote: remote compute (qurcuma-server and wire protocol)

Plan and decisions: `docs/WP-remote-compute-vr.md`. Stages R1 (protocol, server), R2 (client, ssh tunnel, dock selection) R3 (connection loss, capabilities) and R4 (files on the server) are in.

- `protocol.*`: JSON control messages, binary frames and file uploads (little-endian, float32 positions), file policy (`applyFilePolicy`). Qt Core/Gui only.
- `serversession.*`: one authenticated WebSocket connection driving a `LocalBackend`; session directory `<root>/<stamp>/{in,out}` is the process working directory, so a server process serves one session.
- `server_main.cpp`: `qurcuma-server --port N --token T [--root D] [--once]`, listens on 127.0.0.1 only, token of at least 16 characters.
- Connection loss: the server keeps a run going for `--grace` seconds (default 60) with the grab force cleared; the client reconnects (hello with `attach` and the session name, restarting the ssh forward if needed) for 60 s. A run that ends meanwhile hands its `finished` message to the returning client. After the grace period the run is stopped and the session ends. `RemoteServer` holds the one-session policy.
- The server ignores SIGHUP/SIGPIPE so the run survives the ssh session that started it. A connection that never authenticates does not end the session (it idles out after 60 s).
- `welcome` carries `gpuBackends` (compile-time of the server); the dock stores them per host (`remote/gpu/<host>`) and shows them in the GPU combo, all three until the host was connected once.
- Files on the server: `list`/`getFile`/`cancelFile` messages, chunked download (`FileChunk` frames, SHA-256 at the end), only below the shared directories (session root plus `--browse <dir>`, canonical paths, symlinks that leave a root are refused: `resolveBrowsePath`). `remotefiles.*` is a client with its own ssh tunnel and server process (the compute server serves one session); `src/dialogs/remotefilesdialog.*` is File > Remote Files. Uploads go the other way only for run files.
- "Also write the full trajectory on the server" (dock) sets `serverTrajectory`; curcuma then writes `.snapshots/.trj.xyz` (hidden: the worker's molecule has no basename, same for local runs) in the session directory; the `finished` message lists the session files.
- A new curcuma parameter that names a file must be added to `uploadParamKeys()` or `blockedParamKeys()`; the server rejects other path-like strings.
- The server must call `initialize_generated_registry()` before any run (as `src/main.cpp` does), else the first optimisation throws "Parameter ... not found in module".
- `configToJson` adds `optSingleShot` to `simConfigToJson`; lessons do not store it.
- Link measurement: once per second the client logs one `perf:` line (remote log and Output panel): received fps and kB/s, share of this thread spent in `onBinary` (decode, trajectory write, emit), round trip of a `ping`/`pong` (queued behind waiting frames, so it includes server-side buffering), plus the server's last `linkStats` (produced/sent/dropped per s, pending bytes, encode time) and the spacing of frames (mean, sd, max: jitter on the server and on arrival; steps more than three times the running mean are listed as `step:ms`). Pinned by `test_remote_loopback`.
- More lines in `remote.log`: `run:` (settings at start), `gui remote`/`gui local` `rate:` (frames/s received by the dock, not drawn; comparable between local and remote) and `gui viewer` (frames in vs passes done, time in `updateSimulationFrame` split into bond detection and scene sync, GUI event-loop lateness; the GUI part is not covered by a test).
- Sending policy (`serversession.cpp`): at most 60 frames/s (a frame that comes too soon is held, a newer one replaces it; not with `clientTrajectory`, and never a frame with reaction events). A frame is dropped when more is unsent than the link drained in 0.25 s (at least 3 frames, at most 4 MiB, 4 MiB until measured); `finished` reports `framesSent`/`framesDropped`, a held frame goes out before it.
- `remotebackend.*`: `SimulationBackend` over a WebSocket; reads files referenced by the config on this machine and uploads them, writes the trajectory (`writeTrajectory`) from the received frames, no fallback to a local run. `sshtunnel.*`: starts `qurcuma-server --port 0 --token-stdin --once` over `ssh` (BatchMode, token via stdin) and forwards a local port; `QURCUMA_SSH` replaces the ssh binary (tests).
- The host list of the "Compute on" combo (Simulation dock, `QURCUMA_REMOTE`) and of the Remote Files dialog is `~/.ssh/config` plus the computers added in qurcuma (`AddComputerDialog`, `hostprofiles.*`, saved as JSON in QSettings `remote/hosts`; `~/.ssh/config` is never written).
- `SshTunnel` turns exit 127 / "not found" of the server command into a message that names the command and points to Test.
- `SshTunnel` looks a name up in the profiles first and passes `-p`/`-i` before the address; names and addresses are validated (no leading `-`) because they become ssh arguments.
- `hostprobe.*` tests a computer in three steps that are reported one by one (`stepChanged`): ssh login without a prompt; a search for `qurcuma-server` in the PATH and the usual build folders with `--help` as start check (a server command typed by the user is checked first: missing or a directory fails this step and names the server that was found; only its first word is used, and only when it has no shell characters); a real session through `SshTunnel` up to `welcome` and one ping (threads, GPU backends, round trip). The usual failures come with a hint. `AddComputerDialog` (also as test-only for any entry, via the Test button in the dock) shows the steps with icons, greys out all entries while the test runs and lets a saved computer be edited (`HostProfiles::update`; a rename moves the settings kept per computer).
- The choice and the server command per host are stored in QSettings (`remote/...`).
- Tests (built only if Qt6::WebSockets is found): `test_remote_protocol` (format, file policy), `test_remote_loopback` (server and client in one process; final geometry equals the local worker's; RemoteBackend, uploads, trajectory, failure without fallback), `test_remote_ssh` (RemoteBackend through SshTunnel with a python stand-in for ssh).
- More tests: `test_remote_reconnect` (drop during MD and return, no return within the grace period, run ended while away), `test_remote_hosts` (profile validation, storage and editing, ssh arguments, the three test steps against an ssh stand-in and the built qurcuma-server), `test_remote_files` (path policy, listing, chunked download of a multi-chunk file, refusals, full trajectory written and fetched).
- Status: 🤖 AI-generated, ⚙️ machine-tested (loopback and unit tests: protocol, files, reconnect, ssh stand-in, send policy, link measurement). Run over real ssh against a second machine by the operator. Not covered by a test: the dock, the Add computer dialog, the Remote Files dialog, reconnect over a real link, the GUI viewer.
